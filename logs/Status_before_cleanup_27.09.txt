PAPER V2 PIPELINE (25.09), single_segment bound + balanced t_max adaptation
===========================================================================

What is different from results/paper
- Every grid PDMP run uses --bound-mode single_segment --adapt-rule balanced.
  One tangent-line segment per t_max window, the right end is reused as the
  next window's left end, t_max starts at the old grid spacing.
- Every PDMP run has a gradient budget, as in the paper text.
    toy BNNs           G = 200_000
    UCI small/medium   G = 1_000_000 (default PIW and PIW 0.1)
  --n-skeleton is only a ceiling on events, set high enough never to bind.
- Every PDMP run saves S = 4000 draws (--n-resample 4000), after the usual
  20% burn-in by trajectory time.
- Output goes to results/paper_v2/ with the same layout as results/paper/.
- Non-PDMP references (NUTS, NUTS-HS, LBBNN, SVI, tf_*) are copied, not rerun.
- Every command has --resume. Rerunning a command skips every finished
  <sampler>.pt, so after a crash or reboot just run the same command again.
  A run killed mid-sampling restarts that one sampler from scratch.
- Mark each step ☐ -> ✅.

Run everything from the repo root with the venv active
    cd ~/Documents/sticky_samplers/sticky_bnns && source .venv/bin/activate

Machine notes (Mac, 8 cores, 16 GB)
- A shallow UCI job at 1M grads peaks around 3 to 6 GB (the skeleton grows
  with the events actually produced). Run 2 at a time, a 3rd only if memory
  pressure in Activity Monitor stays green. Toy jobs are tiny.
- Deep_narrow at 1M grads needs 20 to 40 GB for the skeleton, so both
  deep_narrow steps run on the GPU server, like v1.
- OMP_NUM_THREADS=2 keeps parallel jobs from fighting over cores. caffeinate -i
  keeps the Mac awake while a job runs (keep it plugged in).
- elapsed_sec in v2 is not directly comparable with v1 (different thread
  count and parallel jobs). Compare gradient_evals instead.

Suggested order
- Mac      step 1 (all four toy jobs at once), then steps 2 and 3, two jobs
           at a time (2a + 2b, 2c + 2d, 3a + 3b, 3c + 3d). About 2 days.
- Server   step 4 on the CPU, step 6 on GPUs 0 and 1, in parallel with the Mac.

6. UCI large [n_in, 256, 128, 64, 1] (deep_wide), SERVER GPUs 0 and 1
   Sticky PDMPs only, K = 1M skeleton points, minibatch 128, PIW 0.05,
   S = 4000.
   What changed vs v1
   - single_segment bound + balanced t_max adaptation. With minibatches every
     window gets a fresh minibatch, so the right-node reuse is off here and a
     window costs 2 minibatch gradients.
   - Resampling is exactly uniform in time over the whole trajectory (a
     streaming reservoir filled stage by stage), and burn-in drops the first
     20% of the TIME, like the small and medium runs.
   - Stage size 10_000 instead of 25_000. With the reservoir the stage size
     no longer affects the samples, it only sets the memory, about 6 to 7 GB
     per job, so two jobs fit on one 23 GB A10.
   v1 took 7 to 9 h per run on one GPU. The old v1 deep_wide job (boston
   splits 3 4, grid bound, PID 1678143) still runs on GPU 3, not needed for v2.
